# Navi v0.6.8

Tag: **`v0.6.8`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.8`, `AGPL-3.0-or-later`, publish configuration `access: public` with `--provenance` through keyless OIDC Trusted Publishing (`environment: release`, `id-token: write`, npm ≥ 11.5.1).

v0.6.7 shipped the edge root page, `/healthz` and the store modularization, but it left the self-serve flow incomplete. Both tenant resolvers — the Worker's and the host's — read `metadata.tenant_id` and then `client_reference_id`. A standard Stripe Payment Link is the one path that needs no integration, and it sends neither: the buyer never passes through code that could attach metadata, so `checkout.session.completed` arrives with `customer: "cus_..."` and nothing this service knew how to name. A purchase therefore answered `400 {"error":"Missing tenant_id"}`, and a sale that did provision through a reference would have its later `customer.subscription.deleted` — carrying only the same `cus_...` — resolve to no tenant at all, leaving the subscription live after cancellation. v0.6.8 derives the tenant from the identifiers Stripe actually sends, in one order, in both runtimes.

## Resolution order

`billingTenantId` is the only place a webhook event becomes a tenant id, so the order is the whole contract. Every candidate is trimmed and must be a non-empty string; the first one that is wins.

| Priority | Source | Applies to | Value |
|---|---|---|---|
| 1 | `data.object.metadata.tenant_id` | every handled event | used verbatim |
| 2 | `data.object.client_reference_id` | every handled event | used verbatim |
| 3 | `data.object.customer` | every handled event | `tenant_${customer}` |
| 4 | `data.object.id` | `checkout.session.completed` only | `tenant_${id}` |

Only when all four are absent does the route answer `400 {"error":"Missing tenant_id"}`. That is the one case where the event carries no identifier this service can bill against, and guessing there would provision a tenant no later event could address.

No API, protocol or storage change. A tenant provisioned by an earlier release keeps its id and key; only events that previously had no resolvable tenant now resolve one. A Worker deployment picks this up on a `wrangler deploy`, which the release pipeline does not perform.

## Honest limits

- The `customer` fallback keys a tenant on the Stripe customer, so one customer that buys twice with different Payment Links shares one tenant. That is the only deterministic choice without metadata, and it is the behavior that makes the later cancellation land on the tenant the first purchase created.
- A `checkout.session.completed` that carries no metadata, no reference, no customer and no session id is still a `400`. Stripe does not send that shape, but the route does not invent an id for it.
- The landing page and `/healthz` remain Worker surfaces; the self-hosted host has its own route table and does not serve them at the same shapes.
- Native amd64 container execution is produced by CI, and was not observed on this arm64 host.

## Post-release update: tier inference

After this tag was published, `main` gained zero-metadata plan inference. Stripe's Payment Link editor exposes no metadata field, so a standard link arrives with `metadata: {}` and the amount billed is the only plan signal. `server/pricing.js` now maps `amount_subtotal`, `amount_total`, the first line item's `price.unit_amount` or `plan.amount` to the Starter, Pro or Enterprise ceiling (`10000`/`50000`/`250000`), keeps explicit `metadata` overrides ahead of it (`unmetered`, `max_events_per_window`, `tier`/`plan`), and both billing paths use the one table. `GET /` renders the four-tier pricing grid, with each paid card's CTA driven by `STRIPE_PAYMENT_LINK_STARTER`, `STRIPE_PAYMENT_LINK_PRO` (or the legacy `STRIPE_PAYMENT_LINK_URL`) and `STRIPE_PAYMENT_LINK_ENTERPRISE`.

This is a follow-up commit, not part of the published release: npm versions are immutable, the tag still points at `c97d57e`, and the `0.6.8` tarball does not contain it. The suite floor on `main` is now **263 passed, 0 failed** after the workflow-compilation work (`257` as of v0.6.9, `254` between v0.6.8 and v0.6.9); the published run recorded **251**.

Both subscription-update edge cases are also closed on `main`: an update that omits `metadata.allowed_origins` now preserves the tenant's existing origin allow-list in both `src/worker.ts` and `server/billing.js`, and `apply_stripe_webhook` treats `p_max_events_per_window: null` alongside a non-null `p_window_seconds` as an explicit switch to an unmetered ceiling.

## Post-release update: 3D landing stage and host parity

`GET /` is now a hardware-accelerated 3D product showcase rather than a flat document, still under `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` and still with zero script elements. Three preset cameras (`rotateX(54deg) rotateZ(-36deg)`, `rotateX(0deg)`, `rotateX(72deg)`), two depth toggles, a 3x3 hover tilt sensor, four pinnable targets and the receipt inspector beside them are all `<input>` state and `:checked` selectors; the token-and-latency calculator is the same mechanism. `server/landing.js` is composed from `server/landing-styles.js`, `server/landing-stage.js` and `server/landing-calculator.js`, and every module under `server/` is now held below **750** lines by `tests/release-pipeline.spec.mjs`. The self-hosted host serves the same document at `GET /`, so its honest limit above — "the self-hosted host has its own route table and does not serve them at the same shapes" — is superseded on `main`: `/healthz` still differs by design (the host reports store mode, tenants and retention), but `/` is now shared.
