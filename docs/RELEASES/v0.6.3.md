# Navi v0.6.3

Tag: **`v0.6.3`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.3`, `AGPL-3.0-or-later`, publish configuration `access: public` with `--provenance` through keyless OIDC Trusted Publishing (`environment: release`, `id-token: write`, npm ≥ 11.5.1).

v0.6.3 closes the last billing hole. v0.6.2 made a subscription become a tenant; what it could not yet do was tell a redelivery from a new event. Stripe resends anything it did not see acknowledged, and a resend used to provision — or suspend — the same tenant a second time. Every verified event now claims its `evt_…` id in a durable ledger before anything is written, so the retry answers `200 {"ok":true,"duplicate":true}` and touches nothing. The same contract is enforced on the self-hosted server, in the log fallback, and at the edge, and the Supabase schema it depends on is now asserted by the suite rather than trusted.

## Provenance

The receipt is published by the commit that carries it, so `evidence.revision` is always one step behind the tag. `evidence.sourceTree` closes that gap: it is a digest over every tracked path outside `reports/`, taken at the gate's revision, and the publish preflight's `provenance-parity` check refuses to proceed unless the tagged tree carries that same digest — or is that revision with nothing outside `reports/` changed.

The digest itself is not repeated here on purpose: a tracked file cannot state the digest of the tree that contains it. The authoritative values are the ones the gate recorded — `evidence.sourceTree` in [reports/release-verification.json](../../reports/release-verification.json) and the same digest printed in the generated [release notes](../../reports/release-notes.md) — and the check that matters is the one the preflight runs against the tagged tree.

## Upgrading

- **Existing tenants need no action.** The ledger is additive: no tenant row, key or window is rewritten, and a deployment that never receives the same event twice behaves exactly as it did.
- **The self-hosted ledger is created on open.** `webhook_events` is created if absent when the store opens, in both backends, so an upgraded process needs no migration step.
- **The Worker needs one more table.** Apply `deploy/supabase-schema.sql` (idempotent) before deploying the Worker. Without `public.webhook_events` the webhook answers `500` rather than provisioning unguarded — a deployment that cannot record an event id must not pretend it can deduplicate one.
- **Version.** `package.json` and the lockfile are `0.6.3`. The Navi protocol stays `0.3.0` and the MCP revision `2025-11-25`: neither changed.

## Honest limits

- **The ledger grows without bound.** One row per billing event is small, but it is not pruned: a tenant's history and Stripe's retention decide when it is safe to forget an id, and guessing that window wrong re-introduces the double-provisioning this release removes.
- **The claim is taken before the work.** A crash between the claim and the tenant write leaves an id claimed by an event that never landed; the compensation only covers a delivery that answered with an error, not a process that died. That window is one request wide, and the alternative — claiming afterwards — lets two simultaneous deliveries both provision.
- **The Worker still has no transaction across the two calls.** Claiming and upserting are separate PostgREST requests; the claim is atomic against a duplicate, but it is not transactional with the `sites` write.
- **The amd64 leg has not been observed here.** It is configured, statically validated and required by the publish gate, but it runs on GitHub's x86_64 runner and the receipt it writes is produced there.
- **The edge schema was proved on PostgreSQL, not through PostgREST.** The file's idempotency, deny rules and upsert keys were exercised against a throwaway PostgreSQL 18 cluster; Supabase's schema cache and project-default grants are the deployment's to verify.
- **Nothing is deployed by this note.** No image is pushed and no service is restarted; the publish is the npm tarball and its provenance attestation.
