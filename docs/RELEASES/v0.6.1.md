# Navi v0.6.1

Tag: **`v0.6.1`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.1`, `AGPL-3.0-or-later`, published configuration `access: public` with `--provenance`.

v0.6.1 is the verification milestone. v0.6.0 gave the deployment a runtime it could describe and stop; what it could not do was *prove* that runtime before shipping, or name its restart evidence unambiguously. This release makes the delivered container a publish gate, verifies the file an operator actually deploys, checks both released architectures on their own hardware, and gives the crash sentinels names that mean what they say.

## Clean-room package canary attestation

The image is not the only artifact a consumer installs. The packed tarball is the other, and packing can drop a manifest export, ship a stale hash or sweep a source file into the archive without one source file changing — so the release gate packs it, unpacks it into an empty directory with no `node_modules` and no link back to this checkout, verifies the extracted files, and then drives the packed `bin/navi-mcp.js` through a live stdio JSON-RPC handshake and a `SIGTERM` teardown. These are the rows the generated notes print, read out of `evidence.canary` in [reports/release-verification.json](../../reports/release-verification.json); the same record is what the publish preflight's `canary-evidence` check requires, so the note and the gate cannot disagree about whether the tarball was proven.

## Provenance

The receipt is published by the commit that carries it, so `evidence.revision` is always one step behind the tag: the gate writes the receipt, and the generated-reports commit that follows is what releases it. `evidence.sourceTree` closes that gap. It is a digest over every tracked path outside `reports/`, taken at the gate's revision, and the publish preflight's `provenance-parity` check refuses to proceed unless the tagged tree carries that same digest — or is that revision with nothing outside `reports/` changed. A report refresh that also moved a source file, a shipped `dist/` artifact or a configuration file therefore stops the publish instead of being waved through as "just the reports".

The digest itself is not repeated here on purpose: a tracked file cannot state the digest of the tree that contains it, and any value written into this document would be the previous revision's. The authoritative values are the ones the gate recorded — `evidence.sourceTree` in [reports/release-verification.json](../../reports/release-verification.json) and the same digest printed in the generated [release notes](../../reports/release-notes.md) — and the check that matters is the one the preflight runs against the tagged tree.

## Upgrading

- **MCP lifecycle sentinels keep their names, and gain meaning.** `NAVI_MCP_STATE_FILE="/var/lib/navi/mcp/state.clean"` now names the successful-teardown marker itself, and dirty evidence for the next boot lives at `/var/lib/navi/mcp/state.dirty`. A volume written by an earlier build — an empty `state.clean` beside a `state.clean.clean` — is classified once from the doubled marker it left behind and then cleaned up, so an upgrade reports the previous owner's real verdict instead of reading a file that merely has the right name as a clean stop. Nothing needs to be deleted by hand.
- **The release gate verifies the production Compose file.** `deploy/docker-compose.prod.yml` requires credentials and a bind address, so the verification runs with generated ones in a disposable project; your deployment is untouched.
- **Version.** `package.json` and the lockfile are `0.6.1`. The Navi protocol stays `0.3.0` and the MCP revision `2025-11-25`: neither changed.

## Honest limits

- **The amd64 leg has not been observed here.** It is configured, statically validated and required by the publish gate, but it runs on GitHub's x86_64 runner and the receipt it writes is produced there. On this arm64 host the amd64 image only runs under QEMU, where Chromium does not install its extra renderer seccomp filter, so that run refuses rather than reporting a pass.
- **A platform absent from the matrix is unverified, not implied.** The notes state only the receipts that exist on the revision they describe.
- **The evidence the preflight reads is the evidence the revision carries.** `evidence.containers` is written by `npm run verify:release` from the receipt files present on the artifact, so it can cite a receipt committed on an earlier run; the fresh per-architecture receipts the release jobs write travel beside it as build artifacts, and the job dependency — not the receipt — is what fails a leg that actually broke.
- **The source-tree attestation covers tracked paths, and only those.** It digests every path tracked at the gate's revision except `reports/`, so it detects a source, script, configuration or rebuilt-bundle change between the gate run and the tag — but it says nothing about a path that is not tracked, and it deliberately tolerates any rewrite under `reports/`, which is where the generated receipt and notes live.
- **Sentinel evidence is not power-loss durability.** The markers attest completed handlers and are flushed and atomically published, but an abrupt host loss around a rename is not covered, and the counter is 0/1 per boot rather than a lifetime crash count.
- **Nothing was published or deployed by this release note.** No image was pushed, no `npm publish` ran from this checkout, and no production Prometheus deployment exists to fire the alert rules.
