# Navi v0.6.5

Tag: **`v0.6.5`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.5`, `AGPL-3.0-or-later`, publish configuration `access: public` with `--provenance` through keyless OIDC Trusted Publishing (`environment: release`, `id-token: write`, npm ≥ 11.5.1).

v0.6.5 removes the last request v0.6.4 left in the webhook's write path. Provisioning read `sites.api_key` with a `GET` before the transaction that wrote the tenant, so that an event without an `api_key` in its metadata could keep the credential a live page was already embedding. That read was a race by construction: two deliveries for the same tenant could both read no key and both write one. The Worker now generates a candidate key and sends it with the event; `public.apply_stripe_webhook(...)` uses it only when it inserts a new row, and keeps the row's key on conflict. One request, no read, no window between them.

## The tag moved, and what that means

`v0.6.5` was created three times before it published: at `a56cec3`, then `81aecff`, then `ec03a90`, the last two because the release workflow and the release gate each needed a fix that had to be inside the tagged tree. The tag now points at `ec03a90` and nothing else, the earlier pushes published nothing from the registry (each failed before `npm publish`), and no consumer ever received a 0.6.5 that was not this tree. The rule this departs from — a published tag is immutable — still holds for every version that reached npm; it did not have to hold for three attempts that did not.

## Provenance

The receipt is published by the commit that carries it, so `evidence.revision` is always one step behind the tag. `evidence.sourceTree` closes that gap: it is a digest over every tracked path outside `reports/`, taken at the gate's revision, and the publish preflight's `provenance-parity` check refuses to proceed unless the tagged tree carries that same digest — or is that revision with nothing outside `reports/` changed.

The digest itself is not repeated here on purpose: a tracked file cannot state the digest of the tree that contains it. The authoritative values are the ones the gate recorded — `evidence.sourceTree` in [reports/release-verification.json](../../reports/release-verification.json) and the same digest printed in the generated [release notes](../../reports/release-notes.md) — and the check that matters is the one the preflight runs against the tagged tree.

## Upgrading

- **Apply the schema before deploying the Worker.** `deploy/supabase-schema.sql` is idempotent and is the whole upgrade: it replaces `public.apply_stripe_webhook` with the ten-argument shape, drops v0.6.4's nine-argument function, re-grants `EXECUTE` to `service_role` only, and ends with `notify pgrst, 'reload schema'`. A Worker deployed against the previous schema sends `p_candidate_api_key` to a function that has no such parameter, and PostgREST answers the call with an error rather than a key.
- **A Worker on the previous schema answers 500, not a phantom key.** The route treats a function response with no key as "no tenant row" and refuses with `500`. That is the deployment ordering made visible instead of handing a customer a credential that authenticates nothing.
- **Existing tenants need no action.** No tenant row, key, window or claim is rewritten. An update that omits `api_key` keeps the key it already has, exactly as it did before; the difference is that the preservation is a `do update` clause rather than a read the Worker made first.
- **Version.** `package.json` and the lockfile are `0.6.5`. The Navi protocol stays `0.3.0` and the MCP revision `2025-11-25`: neither changed.

## Honest limits

- **The candidate is generated per delivery, and usually discarded.** On an update the key the Worker generated is refused by the `do update` and nothing uses it. That is the price of one request: a wasted 32 random bytes beats a read that can race the write.
- **The 500-on-no-key path is not exercised by the suite.** It is reachable only through a schema older than the Worker, which the tests do not stage; the assertion that covers the contract is the one on the candidate in the RPC request body.
- **The schema was proved on PostgreSQL, not through PostgREST.** The functions, their grants, their overload count and their concurrency were exercised against a throwaway PostgreSQL 18 cluster; Supabase's schema cache, project-default grants and the REST layer are the deployment's to verify.
- **The amd64 leg has not been observed here.** It is configured, statically validated and required by the publish gate, but it runs on GitHub's x86_64 runner and the receipt it writes is produced there.
- **Nothing is deployed by this note.** No image is pushed and no service is restarted; the publish is the npm tarball and its provenance attestation.
