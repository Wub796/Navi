# Navi v0.6.7

Tag: **`v0.6.7`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.7`, `AGPL-3.0-or-later`, publish configuration `access: public` with `--provenance` through keyless OIDC Trusted Publishing (`environment: release`, `id-token: write`, npm ≥ 11.5.1).

v0.6.6 was published to the registry without the edge root page, so the deployed `navi-edge` Worker still answered `GET /` with `404 {"error":"Not found"}` — and because every route below the root authenticates, a visiting developer had no public surface that said what the service was or how to call it. v0.6.7 adds that surface. `GET /` renders a static, script-free page from `server/landing.js` with the install line, the loader embed, the sitemap call and the endpoint table, and `GET /healthz` answers from the isolate without touching storage. The store modularization recorded in v0.6.6 is unchanged and still holds: `server/store.js` is 85 lines over five modules, and no file under `server/` reaches the 1,000-line ceiling.

The receipts state the configuration, the platform and the image digest they prove (`compose`, `architecture`, `imageId`), so evidence is not inferred from the file name it sits in or the flag that produced it. Both legs' receipts travel with the release: the publish job downloads them into `reports/container-verification/` and uploads them beside the release receipt as `release-publish`.

## Clean-room package canary attestation

The release gate packs the tarball, unpacks it into an empty directory with no `node_modules` and no link back to this checkout, verifies the extracted files, and then drives the packed `bin/navi-mcp.js` through a live stdio JSON-RPC handshake and a `SIGTERM` teardown. These are the rows read out of `evidence.canary` in [reports/release-verification.json](../../reports/release-verification.json); the same record is what the publish preflight's `canary-evidence` check requires.

## Subresource integrity

The browser bundle is untouched by this release: the change is confined to `src/worker.ts` and `server/landing.js`, neither of which reaches `dist/navi.min.js`. The published hash is therefore unchanged, and three places must still agree with it — `dist/sri.txt`, `reports/build.json` and the served `ETag`.

## Upgrading

```sh
npm i navi-interaction-bridge@0.6.7
```

No API, protocol or storage change: the record shapes, the transaction in `applyWebhookEvent`, the quota window, the one-time checkout claim and the retention prune are the code that shipped in 0.6.6. A Worker deployment that wants the root page and `/healthz` needs a `wrangler deploy` of this revision, and should set `STRIPE_PAYMENT_LINK_URL` as a secret if it wants the self-serve call to action.

## Honest limits

- The landing page is served by the **Worker**. The self-hosted host service has its own route table and does not serve `GET /` or `/healthz` at the same shapes; `/healthz` there is the liveness route the host already exposed.
- The page is uncompiled template text with no build step, so its HTML is asserted by string and header checks in the suite; no browser-layout assertion covers it.
- Native amd64 container execution is produced by CI, and was not observed on this arm64 host.
- Publishing the source does not deploy the Worker. The registry release and the edge deployment are separate operations.
