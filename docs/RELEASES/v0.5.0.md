# Navi v0.5.0

Tag: **`v0.5.0`** — annotated, pointing at the release commit `77613e6` on `main`.
Package: `navi-interaction-bridge@0.5.0`, `AGPL-3.0-or-later`, published configuration `access: public` with `--provenance`.

The bridge between an agent and a real browser, released as a protocol rather than an SDK to adopt: a deterministic action map, guarded execution with settlement receipts, and a discovery path that lets an agent find a host's own runtime instead of injecting its own.

## Subresource integrity

The published hash is the hash of the shipped bytes, and three places must agree with it — `dist/sri.txt`, `reports/build.json` and the served `ETag`. `npm run verify:release` recomputes the digest from `dist/navi.min.js` itself, and `npm run build` cannot finish without writing it.

```
sha384-TmtbTx4Um3FaZ25htbRgiApDW48G3G8321WSwpRCRvAvbvad2hGkA8aOMWiod1Tv
```

Direct embed, with the integrity attribute intact:

```html
<script src="https://your-host/v1/navi.js?key=YOUR_TENANT_KEY"
        integrity="sha384-TmtbTx4Um3FaZ25htbRgiApDW48G3G8321WSwpRCRvAvbvad2hGkA8aOMWiod1Tv"
        crossorigin="anonymous"></script>
```

Or the loader, which is what a tenant should paste (689 bytes, and it is the path that survives an SDK upgrade without touching the page):

```html
<script src="https://your-host/v1/loader.js"
        data-key="YOUR_TENANT_KEY"
        data-sri="sha384-TmtbTx4Um3FaZ25htbRgiApDW48G3G8321WSwpRCRvAvbvad2hGkA8aOMWiod1Tv"></script>
```

## AGPL-3.0 section 13

AGPL-3.0 §13 requires a modified version used over a network to prominently offer remote users its Corresponding Source. The host exposes source-discovery links three ways, unauthenticated and asserted in `tests/auto-discovery.spec.mjs`:

- `Link: rel="source"` on every response, including error responses;
- `GET /v1/source`, which redirects to the repository;
- a `source` field in `/.well-known/navi.json`.

A fork must configure `NAVI_SOURCE_URL` to the complete Corresponding Source of the version it actually serves; linking to the upstream repository is not sufficient for modified code. The suite checks the override with a second origin. These mechanisms support compliance but are not a legal certification.

## Turnkey client setup

The same stdio entry works for both desktop clients. Substitute the absolute path to this checkout (or to the installed package):

```json
{
  "mcpServers": {
    "navi": {
      "command": "node",
      "args": ["/ABSOLUTE/PATH/TO/navi/bin/navi-mcp.js"]
    }
  }
}
```

First run `npm ci --no-audit --no-fund`, `npx playwright install chromium`, and `npm run build` in this checkout. The host/core runtime has no npm runtime dependencies; browser-driving MCP requires a compatible Playwright installation and browser binaries.

**Claude Desktop** — merge that object into `claude_desktop_config.json` (`~/Library/Application Support/Claude/` on macOS, `%APPDATA%\Claude\` on Windows) and restart the app. The file must contain one `mcpServers` object; the copy in [examples/claude-desktop-config.json](../../examples/claude-desktop-config.json) is exactly this shape, and a test asserts the shipped configs are runnable rather than illustrative.

**Cursor** — paste the same object into `~/.cursor/mcp.json` (or `.cursor/mcp.json` in a project). [examples/cursor-mcp.json](../../examples/cursor-mcp.json) is byte-identical to the Claude entry, because one shape is easier to keep correct than two.

**Remote transport** — where the client cannot spawn a process, run the bridge as a server and point the client at it. An open SSE port is an open browser, so the bearer token is mandatory:

```sh
node /ABSOLUTE/PATH/TO/navi/bin/navi-mcp.js --transport sse --port 3001 --host 127.0.0.1 --auth-token "$NAVI_MCP_TOKEN"
```

```json
{
  "mcpServers": {
    "navi": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "http://127.0.0.1:3001/sse", "--header", "Authorization: Bearer ${NAVI_MCP_TOKEN}"]
    }
  }
}
```

## Deploying it

Container configuration for both services, hardened the same way the verified image is:

- [deploy/docker-compose.prod.yml](../../deploy/docker-compose.prod.yml) — host service (`server/index.js`) and MCP bridge (`bin/navi-mcp.js --transport sse`) from one image, as UID/GID 1000, read-only root, capabilities dropped, `no-new-privileges`, a named volume for the telemetry store, and a `/healthz` probe per service. Published to loopback by default; the required variables fail the file loudly when unset.
- [deploy/fly.toml](../../deploy/fly.toml) — the same two services as two process groups, with the store on a Fly volume at `/data`, the host service public behind forced HTTPS, and the bridge on the private network unless an operator publishes it deliberately.

The store is a single path (`/data/telemetry.db`) and `GET /healthz` reports which backend is live. On the pinned Node 22 runtime that is the append-only JSONL log rather than SQLite, so back the directory up rather than assuming a SQLite file.

## Known limitations

- **No live-model numbers are published.** The committed LLM benchmark is a fixture baseline that measures the harness, and it says so in its own heading. Model success rate, step count and cost are only meaningful from a run with a real `LLM_ENDPOINT`/`LLM_MODEL`; those results are written to `reports/LLM-TCR-BENCHMARK-LIVE.md` and never to the baseline.
- **linux/amd64 sandbox verification is delegated to native CI.** The arm64 sandbox posture is verified on this host; under QEMU the amd64 renderer does not install its extra seccomp filter, and the gate refuses that run rather than reporting it as a pass. [containers.yml](../../.github/workflows/containers.yml) verifies each architecture on its own hardware.
- **Fly is not Compose-hardening-equivalent.** Its documented [configuration schema](https://docs.fly.io/reference/configuration) has no `cap_drop`, `no-new-privileges`, read-only-root, tmpfs or custom seccomp controls. Non-root execution is inherited from the image; Fly runtime, volume ownership and Chromium sandbox behavior are not verified here. Use Compose when the exact Docker controls are mandatory.
- **Health endpoints are unauthenticated** by design, so a platform probe can read them. Do not expose `/healthz` as a control plane.
- **Node 22 is Maintenance LTS** as of October 2026. The image is pinned to `22.23.3` for reproducibility, not because the line is newest.
- **No TLS, per-user authorization or tenant browser isolation** inside the container: put an authenticating gateway in front, and apply egress controls before exposing the MCP bridge to less-trusted agents.
- The store is a **single-writer** file; run one host service per volume.

## Post-tag packaging verification

The production Compose file was exercised on native linux/arm64 using a rebuilt image, not the older local image whose SDK hash failed comparison. [Production container receipt](../../reports/production-container-verification.json) records 9/9 checks: UID 1000, zero effective capabilities, `NoNewPrivs: 1`, Chromium renderer sandbox, exact SDK/loader bytes, telemetry surviving restart, bearer rejection, authenticated SSE browser actions and fail-closed startup. The isolated containers and test volume were removed afterwards.

Fly TOML was parsed with Python's `tomllib` and checked for both process commands, the host volume and process-scoped health probes. No Fly deployment or runtime check was performed; its security limitations above remain. No local inference daemon/model was installed, so the live artifact writer was exercised only with a labelled stub in a temporary checkout. No stub numbers were published as empirical model results, and the three committed fixture baseline files remain byte-identical to the tag.
