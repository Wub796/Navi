# Navi v0.6.4

Tag: **`v0.6.4`** — annotated, pointing at the commit on `main` whose `reports/release-verification.json` records the run described below.
Package: `navi-interaction-bridge@0.6.4`, `AGPL-3.0-or-later`, publish configuration `access: public` with `--provenance` through keyless OIDC Trusted Publishing (`environment: release`, `id-token: write`, npm ≥ 11.5.1).

v0.6.4 closes the last window v0.6.3 documented rather than fixed. The edge wrote a webhook's ledger claim, its tenant row and its checkout claim as three separate PostgREST requests, because PostgREST cannot span them in one transaction — so a crash between the claim and the tenant write left an event id claimed by an event that never landed, and two isolates could interleave a quota read with a quota write. Those writes are now three PostgreSQL functions, each one transaction: the claim and the tenant commit together or not at all, the quota charge holds the tenant row, and a one-time key claim is consumed by the `DELETE` that returns it.

## Provenance

The receipt is published by the commit that carries it, so `evidence.revision` is always one step behind the tag. `evidence.sourceTree` closes that gap: it is a digest over every tracked path outside `reports/`, taken at the gate's revision, and the publish preflight's `provenance-parity` check refuses to proceed unless the tagged tree carries that same digest — or is that revision with nothing outside `reports/` changed.

The digest itself is not repeated here on purpose: a tracked file cannot state the digest of the tree that contains it. The authoritative values are the ones the gate recorded — `evidence.sourceTree` in [reports/release-verification.json](../../reports/release-verification.json) and the same digest printed in the generated [release notes](../../reports/release-notes.md) — and the check that matters is the one the preflight runs against the tagged tree.

## Upgrading

- **Apply the schema before deploying the Worker.** `deploy/supabase-schema.sql` is idempotent and is the whole upgrade: it adds the three functions, migrates `checkout_claims` from a millisecond integer to a timestamp (backfilling rows written by v0.6.3), and grants `EXECUTE` to `service_role` only. A Worker deployed against an un-migrated project answers `500` on every write rather than writing unguarded.
- **PostgREST caches the schema.** A `CREATE OR REPLACE` is not visible to PostgREST until its schema cache reloads (`NOTIFY pgrst, 'reload schema'`, or a restart of the REST service). Until then a call to a new function answers `404`, which is a deployment step rather than a bug in this release.
- **Existing tenants need no action.** No tenant row, key or window is rewritten by the migration, and a deployment that never sees a duplicate behaves exactly as it did.
- **The Worker no longer compensates.** There is no separate ledger request and no `releaseWebhookEvent` equivalent at the edge: a failed call is a transaction that aborted, which is the opposite of a claim left behind.
- **Version.** `package.json` and the lockfile are `0.6.4`. The Navi protocol stays `0.3.0` and the MCP revision `2025-11-25`: neither changed.

## Honest limits

- **The quota row lock serialises a tenant's writes.** `for update` is what makes the ceiling exact, and its cost is that two simultaneous ingestions for the same tenant queue rather than proceed. That is one short lock on one row; a tenant at thousands of events per second would want a partitioned counter rather than this.
- **The charge and the map write are still two statements.** The function is atomic with itself; the `navigation_maps` upsert that follows it is a second request. A failure between them charges a tenant for an event that was not stored — the same behaviour v0.6.3 had, now bounded to the storage write instead of the whole ledger.
- **The schema was proved on PostgreSQL, not through PostgREST.** The functions, their grants and their concurrency were exercised against a throwaway PostgreSQL 18 cluster; Supabase's schema cache, project-default grants and the REST layer are the deployment's to verify.
- **The behavioural schema tests need a local server.** Without `initdb`/`pg_ctl` on the host they skip with that reason, and the static contract in `release-pipeline.spec.mjs` is what still runs. The gate counts skipped tests separately and still compares the passing count to the floor, so that host fails the release gate with a legible reason rather than passing on tests that never ran.
- **The amd64 leg has not been observed here.** It is configured, statically validated and required by the publish gate, but it runs on GitHub's x86_64 runner and the receipt it writes is produced there.
- **Nothing is deployed by this note.** No image is pushed and no service is restarted; the publish is the npm tarball and its provenance attestation.
